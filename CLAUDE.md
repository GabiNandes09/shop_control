> Este arquivo é lido automaticamente pelo Claude Code ao abrir este diretório. Ele documenta o estado do app até o momento, para que qualquer nova conversa (neste ou em outro chat) tenha contexto completo sem precisar re-explorar tudo do zero.

## O que é o app

App Android pessoal (não publicado) para controle de gastos de compras via leitura do QR Code da **NFC-e** (nota fiscal de consumidor eletrônica, SEFAZ-SP). Ao escanear, o app baixa o HTML da nota, faz parsing e salva estabelecimento, compra e produtos localmente. Em cima disso, oferece análises de gasto (mês, produto, categoria, estabelecimento).

- Repositório: https://github.com/GabiNandes09/shop_control
- Único desenvolvedor/usuário: o próprio dono do repo, testando no próprio celular (Xiaomi M2101K6I) conectado via ADB wireless.

## Stack técnica

- Kotlin 2.3.10, Jetpack Compose (Material3), sem XML views (só o `MainActivity` + tema pré-Compose para status bar).
- **Koin** 4.2.2 para DI (não Hilt/Dagger).
- **Room** 2.8.4 para persistência local (SQLite), banco `shop_control.db`, **versão 9** (migrations reais, ver abaixo — nunca usar `fallbackToDestructiveMigration`, sempre migração SQL preservando dados).
- **Retrofit + OkHttp + kotlinx.serialization** para buscar o HTML da NFC-e (`NfceApi`, base URL da SEFAZ-SP).
- **Jsoup** para parsear o HTML da nota (`NfceHtmlParser`).
- **CameraX + ML Kit Barcode Scanning** para o scanner de QR Code (`utils/QrCodeScanner.kt`).
- **Navigation Compose** para navegação (`AppNavigation.kt`), com bottom bar de 4 abas.
- `material-icons-extended` (não só `-core`, pois ícones como `CameraAlt` não estão no core).
- `minSdk 26`, `compileSdk/targetSdk` recentes (37/36).

**Convenções importantes já validadas com o usuário:**
- Um `UseCase` por operação, mesmo que dois usecases sejam muito parecidos (ex.: `GetComprasUseCase` e `GetCompraByIdUseCase` ficam separados — decisão explícita, não juntar).
- Filtros (mês, nome, categoria, ordenação) são sempre aplicados **client-side** no ViewModel (cache da lista "original" + função `aplicarFiltros()`), não em múltiplas queries SQL — mais simples de combinar vários filtros.
- Datas são `String` no formato `dd/MM/yyyy HH:mm:ss` (como a NFC-e retorna), parseadas via `utils/parseDataCompra` → `LocalDate`. Não há coluna de data real no banco. **Regra do sistema pra `ORDER BY` em SQL**: `ORDER BY dataCompra DESC` puro faz comparação léxica — como o formato começa pelo *dia*, não pelo ano, isso ordena por dia-do-mês primeiro e intercala meses/anos diferentes de forma errada (ex. "27/07/2026" cai entre "28/08/2026" e "26/08/2026", porque o comparador nunca olha o mês). Bug real, descoberto quando a base passou a ter dados de vários meses (import da planilha Finanças 2026) — antes disso, com dados só de um mês, passava despercebido. Toda ordenação por data em SQL reconstrói a string no formato `yyyyMMddHHmmss` na hora, via `substr`, sem alterar o dado armazenado: `substr(dataCompra,7,4) || substr(dataCompra,4,2) || substr(dataCompra,1,2) || substr(dataCompra,12,8) DESC`. Usado em `CompraDao.getCompras`/`getComprasByEstabelecimento`, `RendaDao.getRendaComDados`, `ARecebimentoDao.getARecebimentosComDados`, `ProdutoDao.getHistoricoProduto` — todo `ORDER BY` novo sobre um campo de data desse formato deve seguir o mesmo padrão. Cada uma dessas queries também ganhou `, id DESC` como desempate (mais novo primeiro por data de criação no app quando a data de movimentação é igual) — o autoincrement funciona como proxy de `createdAt`, mesmo padrão já usado no alerta de preço.
- Toda tela com filtros usa o componente `FilterToggleChip` + `FilterOverlay` (chip "Filtros" que abre um painel **flutuante sobre o conteúdo**, não empurra a lista pra baixo — decisão explícita do usuário).
- **Filtro de data**: `domain/model/DateRange.kt` (start/end `LocalDate`, `DateRange.currentMonth()` como padrão, operador `in`) + componente `DateRangeSelector` — um único calendário Material3 (`DateRangePicker`/`rememberDateRangePickerState`, aberto num `Dialog` próprio em vez de `DatePickerDialog`, que é pensado só pro `DatePicker` compacto) pra selecionar início e fim juntos, mais duas setas (`ChevronLeft`/`ChevronRight`) que deslocam o range inteiro pra trás/frente pelo próprio tamanho em dias (`spanDias = fim − início + 1`) — reaproveitando o range atual como "página" de navegação. Usado em Registros, Todos os Produtos, Estabelecimentos, Gasto por Categoria, Detalhe de Estabelecimento, Home, Renda e Análise.
  - **Duas pegadinhas do `DateRangePicker` dentro de um `Dialog` custom, ambas resolvidas por tentativa e erro no dispositivo real** (a única forma confiável de validar, já que emulador/preview não reproduz o bug): (1) `Dialog` do Compose mede o conteúdo em `wrap_content` **de altura** independente de `DialogProperties(usePlatformDefaultWidth = false)` (que só afeta largura) — `Modifier.fillMaxHeight(fração)` dentro dele não tem contra o que se ancorar e vira no-op. Resolvido calculando largura/altura em dp explícitos a partir de `LocalConfiguration.current` (`screenWidthDp`/`screenHeightDp`) em vez de `fillMaxWidth()`/`fillMaxHeight()`. (2) mesmo com o `Dialog` já ocupando a tela inteira, o **headline padrão** do `DateRangePicker` (formato longo "3 de setembro de 2026") não cabe duas vezes lado a lado numa tela de celular — sempre estoura, não é um problema de contêiner. Resolvido substituindo os slots `title`/`headline` (parâmetros do próprio `DateRangePicker`, não do nosso wrapper) por composables customizados enxutos, reaproveitando `DATA_DISPLAY_FORMATTER` (`dd/MM/yyyy`) — muito mais curto, nunca quebra. **`showModeToggle` continua `true`** (default) — o ícone de lápis pra alternar pro modo de digitação direta (dois campos de texto, "Data de início"/"Data de término") é útil e não tem o mesmo problema de largura do headline. **Regra do sistema (não só a Home persiste mais)**: a Home continua sendo a única tela que **persiste** o intervalo entre sessões (`HomeDateRangeRepository`, DataStore Preferences) — mas agora ela também é a **fonte do valor inicial pra todas as outras telas**: cada ViewModel injeta `GetHomeDateRangeUseCase` e lê o range da Home **uma vez, no `init`** (`getHomeDateRange().first()`), usando isso como ponto de partida em vez de `DateRange.currentMonth()`. Dali em diante o filtro daquela tela é **só local** (mesmo padrão de sempre — não escreve de volta pra Home, reseta pro valor da Home a cada reabertura da tela). **Produtos Cadastrados** fica de fora (catálogo de navegação, sem data). **A Receber** também fica de fora (sem filtro de período — ver Feature A Receber).
- Toda tela usa `ScreenHeader` (título + botão de voltar opcional + slot `actions` opcional pra ícones à direita, ex. a engrenagem de opções em Produto/Estabelecimento). As 3 abas da bottom bar (Home/Registros/Configurações) **não** passam `onBackClick` (são destinos de nível superior, sem seta de voltar).
- **Regra do sistema: todo texto cadastrado pelo usuário entra com a primeira letra maiúscula** (`utils/capitalizarPrimeiraLetra`, trim + `replaceFirstChar { it.titlecase(Locale("pt-BR")) }`) — aplicado no repository, no momento de gravar, nunca na UI (mesmo ponto onde já acontecia dedup/trim). Cobre: nome/endereço/apelido de Estabelecimento, nome/apelido de Produto, nome de Categoria (produto e renda), nome de Fonte de Renda, descrição de Renda e de A Receber, nome de despesa Fixa/Parcelada. **Não se aplica a dados vindos de fora do controle do usuário** (nome/endereço de estabelecimento parseados de uma NFC-e — `CompraRepository.save` — ficam como a nota trouxe) nem a códigos (EAN/código de barras).
- **Ações "perigosas"/pouco usadas ficam atrás de uma engrenagem na topbar** (`ScreenHeader(actions = {...})` com `IconButton(Icons.Filled.Settings)` + `DropdownMenu`), não como botão fixo no corpo da tela — padrão usado em `ProductDetailScreen` ("Vincular a outro produto") e `EstablishmentDetailScreen` ("Vincular a um estabelecimento com CNPJ", só aparece no menu quando `cnpj.isBlank()`).

## Banco de dados

Entidades (`@Entity`): `EstabelecimentoEntity` (nome, cnpj, endereco, **apelido** nullable, **categoriaId** nullable — ver "Categoria por Estabelecimento" abaixo), `ProdutoEntity` (nome, codigo, categoriaId — `0` = sem categoria, sentinela, não FK), `CategoriaEntity` (nome), `CompraEntity` (estabelecimentoId, dataCompra, valorTotal, chaveNfce, **origem** — enum `OrigemCompra` `NFC_E`/`MANUAL`, Room grava nativamente como TEXT via `.name`, sem TypeConverter, **dividida** `Boolean` default `false` — ver "Divisão de Conta" abaixo), `ItemCompraEntity` (compraId, produtoId, quantidade, valorUnitario, valorTotal), `DivisaoContaEntity` (compraId, fonteRendaId, valor — uma linha por participante da divisão, não inclui o dono da conta).

**`EstabelecimentoEntity.cnpj` continua não-nulo — decisão deliberada**: em vez de tornar o campo nullable (o que exigiria uma migração de recriação de tabela), a Feature 1 (cadastro manual) reaproveita a convenção que já existia para falhas de parsing da NFC-e: `cnpj = ""` significa "sem CNPJ". `EstabelecimentoDao.findByNome` (COLLATE NOCASE) faz o dedup por nome quando não há CNPJ. `endereco` segue o mesmo espírito (`""` quando não informado). Mesma lógica para `EstabelecimentoDao.findByCnpj`, que nunca deve ser chamado com string vazia (ver `CompraRepository.saveManual`, que não usa dedup por CNPJ).

**Deduplicação na gravação NFC-e** (`CompraRepository.save`): reaproveita estabelecimento existente por CNPJ e produto existente por nome (em vez de sempre inserir novo). Também detecta compra já salva (mesmo CNPJ + data/hora) e evita duplicar. Itens duplicados dentro da mesma nota (mesmo nome + mesmo valor unitário) são somados no parser antes de salvar.

**Cadastro/edição manual de compra** (`CompraRepository.saveManual`, Feature 1): dedup de estabelecimento por nome (trim + case-insensitive); `compraId = 0L` cria uma compra nova (`origem = MANUAL`), qualquer outro valor sobrescreve data/estabelecimento/valorTotal e substitui todos os itens (`deleteItensByCompraId` + reinserção) — edição é "tudo ou nada" num único Salvar, não CRUD granular persistido a cada ação. Produto novo exige confirmação explícita do usuário (`FindProdutoByNameUseCase` retorna null → UI pede confirmação → `CreateProdutoUseCase`). Item duplicado (mesmo `produtoId`) na mesma compra em edição é bloqueado no ViewModel, não no banco.

**Cadastro manual de estabelecimento** (`EstablishmentListScreen`, FAB "+"): `AddEstablishmentDialog` (nome obrigatório, CNPJ/endereço/apelido opcionais) → `EstabelecimentoRepository.addEstabelecimento` reaproveita o mesmo dedup por CNPJ (se preenchido) ou por nome (se não) já usado em `CompraRepository.saveManual`. **Importante**: `EstablishmentListViewModel` deixou de agregar a partir só de `getTodasComprasComEstabelecimento()` (INNER JOIN com `compras` — um estabelecimento recém-criado sem nenhuma compra simplesmente não aparecia na lista) e passou a partir de `GetAllEstabelecimentosUseCase` (todos os estabelecimentos), calculando o gasto de cada um a partir das compras filtradas (`0.0` quando não há compra no período) — assim um estabelecimento novo aparece na lista imediatamente, com R$ 0,00, em vez de sumir até a primeira compra.

**Vínculo de estabelecimento sem CNPJ com um com CNPJ** (`EstabelecimentoDao.linkToEstabelecimentoComCnpj`, Feature 1.5): reaponta todas as `compras.estabelecimentoId` do estabelecimento sem CNPJ pro estabelecimento com CNPJ e apaga o registro sem CNPJ. Unidirecional, irreversível, com `ConfirmDialog` antes de executar. Acessível em `EstablishmentDetailScreen` só quando `estabelecimento.cnpj.isBlank()`.

**Agregações client-side por intervalo de data** (Feature 2): como as datas são `String` (não dá pra filtrar por intervalo em SQL de forma confiável), todo o agrupamento por data passou a ser feito em Kotlin a partir de datasets "crus" (por item/por compra), igual ao padrão que `ProductListViewModel` já usava:
- **Estabelecimentos** (ranking): `EstabelecimentoDao.getComprasComEstabelecimento()` retorna todas as compras com dados do estabelecimento (`EstabelecimentoCompraComData`); `EstablishmentListViewModel` filtra por `DateRange` e agrupa em `EstabelecimentoGasto` (mesma classe de antes, só que agora montada em memória em vez de vir de uma query `GROUP BY` all-time).
- **Categorias** (gráfico de gasto): `CategorySpendingViewModel` passou a usar `GetProdutoItensComDataUseCase` (já existia, reaproveitado de Produtos) em vez de uma query dedicada; agrupa em `CategoriaGasto`.
- **Home** ("Valor gasto" + card "Produtos"): `HomeViewModel` também passou a usar `GetProdutoItensComDataUseCase`, filtrando pelo `DateRange` persistido e somando/agrupando em memória — substituiu `GetMonthlySpendingUseCase` (fixo no mês atual) e `GetProdutosGastoUseCase` (all-time), ambos removidos.
- Consequência: as queries SQL `GROUP BY` all-time (`getEstabelecimentosGasto`, `getCategoriasGasto`, `getProdutosGasto`) e seus usecases foram **removidos** (substituídos pelos datasets crus acima). `getProdutoGastoById` (detalhe de produto) não foi afetado — fica de fora do escopo da Feature 2.

**Produto: EAN, apelido e merge** (Features 5, 6, 7 — todas na mesma tela, `ProductDetailScreen`, por decisão do próprio planejamento): `ProdutoEntity` ganhou `codigoBarras` (nullable, migração v4→v5) e `apelido` (nullable, mesma migração). `ProductSummaryCard` ganhou linhas de EAN e apelido (cada uma com um botão "+" que abre um diálogo — `EanInputDialog`/`TextInputDialog`), seguindo o mesmo padrão do botão de categoria. `EanInputDialog` tem um ícone de câmera que abre `BarcodeScannerDialog` (um `Dialog` em tela cheia, não uma rota de navegação — evita o problema de "retornar um resultado" da Navigation Compose) reaproveitando `CameraPreview`/`startScanner` (generalizados para aceitar uma lista de `formats` do ML Kit — o scanner de NFC-e continua fixo em `FORMAT_QR_CODE`, o de produto usa EAN-13/EAN-8/UPC-A/UPC-E/CODE_128). Merge (`ProdutoDao.mergeProdutos`) segue exatamente o padrão já usado para estabelecimentos sem CNPJ (Feature 1.5): botão "Vincular a outro produto" → `ProductPickerDialog` → `ConfirmDialog` (irreversível) → reaponta `itens_compra.produtoId` pro produto de destino e apaga o produto de origem.

**Categorias de Produtos: FAB, grupos, busca e vínculo em lote**: `CategoryManagementScreen` trocou a linha de "adicionar categoria" (campo + botão inline) por um **FAB** que abre `TextInputDialog` (mesmo componente já usado pra editar) — `CategoryManagementState.showAddDialog`. `CategoryPickerDialog` (usado em toda parte que liga um produto/compra a uma categoria — `ProductDetailScreen`, `ManualPurchaseEntryScreen`, e reaproveitado também como picker de **grupo**) ganhou: **busca por nome** (campo de texto local no próprio diálogo, filtra a lista) e, quando o chamador passa `onCreateCategory` (nulo no caso do picker de grupo — ver abaixo), uma linha **"Criar categoria \"X\""** que aparece quando o texto buscado não bate com nenhuma categoria existente — cria e já seleciona (`AddCategoriaERetornarIdUseCase`/`CategoriaRepository.addCategoriaERetornarId`, dedup-ou-cria retornando o id, distinto do `AddCategoriaUseCase` que só retorna `Boolean` e continua sendo usado pelo fluxo "Nova categoria" do FAB).
- **Agrupamento de categorias** (`CategoriaEntity.grupoId: Long?`, self-referencing — uma categoria pode ser "grupo" de outras sem precisar de tabela nova, qualquer categoria serve como grupo): cada linha de `CategoryListItem` mostra um ícone (`Icons.Filled.Category`) que abre o mesmo `CategoryPickerDialog` (sem `onCreateCategory`, filtrando a própria categoria da lista) pra escolher/trocar o grupo; o nome do grupo aparece como subtítulo ("Grupo: Itens de mercado"). Sem limite de profundidade nem checagem de ciclo — decisão pragmática de escopo mínimo, já que o caso de uso descrito (agrupar "alface"/"queijo"/"água mineral" em "itens de mercado") é só um nível.
- **Vincular vários produtos a uma categoria de uma vez** (`Icons.Filled.Link` em cada `CategoryListItem`): abre `LinkProdutosToCategoriaDialog` — lista todos os produtos com checkbox (pré-marcados os que já têm essa categoria) + busca por nome (necessário, o catálogo pode ter centenas de produtos). "Salvar vínculos" faz um diff contra o estado original (`produtosSelecionados` vs. produtos que já tinham essa categoria) e aplica só a diferença: `ProdutoDao.updateCategoriaForIds` em lote pros que entraram (seta a categoria) e pros que saíram (seta `0L`, sentinela "sem categoria") — reaproveita a mesma convenção de `ProdutoEntity.categoriaId` já documentada acima.

**Ícones de cadastro nos cards de produto** (`ProdutoCadastroIcons`, componente compartilhado em `ProductGastoRow.kt`): todo card de produto em lista (`ProductGastoRow` — Análise, Todos os Produtos; `ProductCatalogItem` — Produtos Cadastrados) mostra dois ícones pequenos, coloridos (`colorScheme.primary`) quando presente e apagados (`onSurfaceVariant` com alpha) quando ausente — um pra código de barras (`Icons.Filled.QrCode`) e um pra categoria (`Icons.AutoMirrored.Filled.Label`). Exigiu adicionar `codigoBarras` em `ProdutoItemComData` (e na query `ProdutoDao.getProdutoItensComData`), já que o card de "gasto" é montado a partir desse dataset agregado por item, não direto da `ProdutoEntity`.

**Apelido de produto propagado em todo o app**: o componente `EstablishmentName` foi generalizado e renomeado pra `EntityName` (mesma lógica — nome grande, ou apelido grande + nome pequeno embaixo — reutilizável pra qualquer entidade com nome+apelido). Usado agora tanto pra estabelecimento quanto produto: `ProductListItem` (itens do detalhe de compra), `ProductGastoRow` (Home, Todos os Produtos), `ProductSummaryCard` (detalhe de produto), `ProductCatalogItem` (Produtos Cadastrados). `ProdutoGasto` e `ProdutoItemComData` ganharam campo `apelido`/`apelidoProduto` (populado nas queries SQL correspondentes) pra isso funcionar sem query extra. Busca por nome em Produtos Cadastrados e Todos os Produtos também passa a considerar o apelido (mesmo padrão já usado em Estabelecimentos).

**Alerta de aumento/redução de preço** (Feature 3, `PurchaseDetailViewModel`): calculado em tempo de consulta, nenhum campo novo persistido. `CompraDao.getTodosPrecos()` retorna `ItemPrecoHistorico(compraId, produtoId, dataCompra, valorUnitario)` para **todos** os itens já comprados; `PurchaseDetailViewModel` combina esse fluxo com o da compra aberta (`combine`) e, pra cada item, busca a ocorrência anterior do mesmo produto — "anterior" = menor em `(dataCompra, compraId)` comparado à compra atual (desempate por `compraId`, que funciona como proxy de `createdAt` porque é autoincrement e a tabela nunca tem linhas deletadas-e-reinseridas fora de ordem — evita precisar de uma coluna `createdAt` nova). Preço igual ou sem ocorrência anterior → sem alerta (`Map<itemId, PriceAlert>` não tem entrada pra esse item). `ProductListItem` ganhou `onClick` (abre o detalhe do produto) e exibe a seta colorida + **a diferença entre o preço atual e o anterior** (não o valor anterior em si) quando há `priceAlert` — `PriceAlert.diferenca = abs(valorAtual - valorAnterior)`, calculada no momento em que o alerta é montado em `calcularAlertasPreco`.

**Nota importante sobre `ProdutoEntity.codigo`**: é o código do produto como aparece na NFC-e (`.RCod`), que é o código **interno do estabelecimento**, não necessariamente o código de barras/EAN real (frequentemente coincidem na prática, mas não é garantido). Não há campo dedicado de código de barras nem validação de EAN.

**Receita** (`RendaEntity`, aba própria "Renda" na bottom bar — segunda rodada de planejamento, `ShopControl_Planejamento.md` "Feature 1"): registro de entradas de dinheiro (salário, freela, presente etc.), com categoria (`RendaCategoriaEntity`, CRUD próprio em Configurações → "Categorias de Renda", separado das categorias de produto) e fonte (`FonteRendaEntity`, autocomplete-ou-cria igual ao padrão de estabelecimento, com lista própria "Fontes" e tela de detalhe por fonte).

- **Motor de recorrência** (`RendaRepository`): quando o usuário marca uma renda como recorrente na criação, o app gera **12 ocorrências futuras de uma vez** (`gerarLote`), uma por mês, encadeadas por `origemRecorrenteId` (cada linha aponta pra linha anterior da série — lista ligada, não um `groupId` compartilhado). Editar uma ocorrência recorrente propaga a mudança "essa e todas as futuras já geradas" (`collectForwardChain`, percorre a cadeia pra frente a partir do id editado). Excluir uma ocorrência recorrente (`deleteRendaForward`) apaga essa e todas as futuras da cadeia, e desliga a flag `recorrente` no novo "fim" da série (a ocorrência anterior à excluída) pra parar a extensão automática.
- **Extensão automática**: `VerificarEEstenderSeriesRendaUseCase`, chamado uma vez no `init` do `HomeViewModel` (toda vez que o app abre), verifica se o fim de alguma série recorrente ativa está a menos de 2 meses de acabar e, se sim, gera mais 12 meses — o usuário nunca vê uma série "secar".
- Editar/excluir uma ocorrência **não-recorrente** é simples (linha única, sem propagação).

**Despesas Fixas e Parceladas** (`CompraEntity.tipo: TipoCompra` = `VARIAVEL` | `FIXA` | `PARCELADA` | `RAPIDA`, "Feature 2" do novo planejamento): reaproveita a própria tabela `compras` em vez de criar uma tabela nova — uma compra `FIXA`/`PARCELADA`/`RAPIDA` não tem linhas em `itens_compra`, tem `nome` e `categoriaId` próprios (a categoria aqui é a **mesma** tabela `categorias` de produto, não a de renda) e representa a despesa inteira como um valor único.
- **RAPIDA** (lançamento avulso não-recorrente, ex. um rolê/despesa pontual num bar): mesmo formato de "nome + valor + categoria + estabelecimento" de `FIXA`/`PARCELADA`, mas sem nenhuma semântica de recorrência/parcelamento — um único `insert` em `CompraRepository.saveFixaOuParcelada` (branch `TipoCompra.RAPIDA` do `when`), sem `origemRecorrenteId`, sem `totalParcelas`, sem lote. Existe justamente pra não forçar itemização (`VARIAVEL`) nem poluir o catálogo de produtos/histórico de preço em despesas cujo valor e local mudam a cada ocorrência. Delete é o simples (`deleteCompra`, não `deleteCompraForward` — cai no mesmo `else` de `PurchaseDetailViewModel.delete()` que trata qualquer tipo não-FIXA/PARCELADA).
- **FIXA** (aluguel, assinatura, etc.): mesmo motor de recorrência da Renda, adaptado (`CompraRepository.saveFixaOuParcelada` / `gerarLoteFixa` / `deleteCompraForward` / `verificarEEstenderSeriesFixa`, mesmo lote de 12, mesmo limiar de 2 meses, chamado no `init` do `HomeViewModel`). Como o campo `recorrente` da Renda não existe em `CompraEntity` (não estava na lista de campos do planejamento), a mesma função é cumprida por um campo `ativo: Boolean` (decisão pragmática, documentada aqui: o planejamento diz explicitamente que a regra de cascata de exclusão da Compra é "igual à da Feature 1", que depende desse tipo de flag) — desligado no pai do novo fim da série quando uma exclusão-em-cascata trunca a cadeia.
- **PARCELADA** (compra parcelada em N vezes): todas as parcelas são criadas **de uma vez só** (não em lote de 12), compartilhando a mesma `dataCompra` (a data original digitada pelo usuário, é sempre isso que aparece na UI) mas cada uma com uma `dataCompetencia` distinta (avança um mês por parcela — usada só pra filtro/agregação por período, nunca exibida). Suporta lançar retroativamente parcelas já pagas (`parcelasJaPagas`): a série é montada com as parcelas anteriores primeiro, então a raiz real da cadeia (`origemRecorrenteId`) pode não ser a parcela que o usuário digitou diretamente, e sim a primeira parcela paga.
- **`dataParaFiltro`** (extension property em `CompraEntity`, `CompraComData`, `EstabelecimentoCompraComData` e `EstabelecimentoCompraData`): `if (tipo == PARCELADA) dataCompetencia else dataCompra`. Todo filtro/agregação por período no app (Registros, Home, Gasto por Categoria, Estabelecimentos) usa esse campo em vez de `dataCompra` direto, senão uma compra parcelada apareceria inteira no mês em que foi lançada em vez de espalhada pelos meses das parcelas.
- **Contribuição nos totais**: unificado na leva "Categoria por Estabelecimento" (ver abaixo) — `HomeViewModel.valorGasto` soma `Compra.valorTotal` de `GetComprasComDataUseCase` (todos os tipos, sem distinção) filtrado por `dataParaFiltro` no período. Histórico: originalmente (Feature 2 do planejamento anterior) somava duas fontes em paralelo — itens (`VARIAVEL`) + `GetComprasComDataUseCase` filtrado por `tipo != VARIAVEL` — porque só `FIXA`/`PARCELADA`/`RAPIDA` tinham `categoriaId`/`valorTotal` confiável; deixou de ser necessário quando `VARIAVEL` passou a gravar `valorTotal` corretamente (item cheio) e `categoriaId` também.
- **Categoria de produto agora bloqueia exclusão também por uso em compra e em estabelecimento**: `CategoriaDao.countUsage` soma uso em `produtos.categoriaId`, `compras.categoriaId` **e** `estabelecimentos.categoriaId`; `CategoriaRepository.deleteCategoria` retorna `Boolean` (bloqueado = `false`) em vez de `Unit`.
- **Tela "Compras Parceladas"** (Configurações): agrupa compras `PARCELADA` em séries (percorre `origemRecorrenteId` pra trás até a raiz, em memória, sem query extra), mostra a parcela atual (última cuja `dataCompetencia` já chegou), progresso "X/Y", soma do compromisso mensal total, e seções Ativas/Concluídas (com toggle).
- **Registros** ganhou filtro por tipo (Todas/Variáveis/Fixas/Parceladas/Rápidas, chips dentro do painel de filtro existente) além do filtro de período já existente.

**Saldo e Balanço** (`GetBalancoMensalHistoricoUseCase`, "Feature 3" do novo planejamento): amarra Renda e Despesas — `Saldo(período) = Renda(período) − Compras(período)`, onde Compras já soma os três tipos (item-based + `FIXA`/`PARCELADA` direto, mesma lógica de `HomeViewModel.valorGasto`). Sem saldo acumulado — cada período é isolado.

- **Card "Saldo" na Home**: primeiro elemento da tela (antes até do "Valor gasto"), respeitando o mesmo `DateRange` persistido. Cor do valor (verde/vermelho, `PositiveValueColor`/`NegativeValueColor` em [StatCard.kt](app/src/main/java/com/rogue/shopcontrol/presentation/components/StatCard.kt)) conforme o sinal; subtítulo mostra a composição ("Renda R$X − Despesas R$Y"). `StatCard` ganhou um parâmetro opcional `valueColor` pra isso. Toque no card navega pra "Balanço".
- **Tela "Balanço"** (Análises): gráfico próprio (`BalancoChart.kt`, Canvas customizado — barras de Renda/Despesas lado a lado por mês + linha de Saldo sobreposta, com baseline dinâmica pra acomodar saldo negativo) em vez do `AnalyticsContent`/`ChartEntry` genérico (que só suporta um valor por rótulo) — janela fixa dos **últimos 12 meses**, sem respeitar nenhum `DateRange` de tela (mesmo precedente da "Comparação de Gastos"). Abaixo do gráfico, lista mês a mês com Renda/Despesas/Saldo.
- `GetBalancoMensalHistoricoUseCase` combina `CompraRepository.getCompras()` (usa `Compra.valorTotal` direto via `dataParaFiltro`, já correto pra `FIXA`/`PARCELADA` sem qualquer ajuste extra) com `RendaRepository.getRendaComDados()`, agrupando ambos por mês.

**A Receber** (`ARecebimentoEntity`, nova seção "Renda" em Configurações, "Feature 4" do novo planejamento): valores que o usuário **vai** receber (normalmente de terceiros), diferente de Fonte de Renda que só registra dinheiro já recebido. Reaproveita `RendaCategoria` e `FonteRenda` (mesmas tabelas da Renda) — não tem categoria/fonte próprias.

- **Três tipos, mesmo modelo da Compra**: `PONTUAL` (avulso) | `FIXA` | `PARCELADA`, com o mesmo motor de recorrência (geração eager em lotes de 12 pra `FIXA`, dia fixo 10; série completa de uma vez pra `PARCELADA`, sem backfill retroativo — diferente da Compra Parcelada). `tipo` imutável após salvo. Campo `ativo: Boolean` (mesma justificativa pragmática usada em `CompraEntity` — não está na lista de campos do planejamento, mas é necessário pra implementar a regra de cascata que a Feature 4 explicitamente herda das Features 1/2).
- **`PARCELADA` avança a `dataPrevista` mês a mês com clamp de fim de mês** (diferente da Compra Parcelada, que trava numa única data): `LocalDate.plusMonthsClamped()` (novo utilitário em [DateUtils.kt](app/src/main/java/com/rogue/shopcontrol/utils/DateUtils.kt)) ancorado sempre no dia original da primeira parcela (não encadeado a partir da parcela anterior já clampada), pra não degradar o "dia de vencimento" mês a mês (ex. dia 31 → fev vira 28, mar volta a ser 31, não fica preso em 28).
- **Virar Renda ao marcar como pago** (`ARecebimentoRepository.marcarComoPago`): cria um lançamento avulso em `Renda` (`RendaRepository.criarRendaAvulsa`, novo método — `recorrente = false`) e grava `rendaGeradaId` no `ARecebimento`. Se o mês da data de pagamento (sempre "hoje") for diferente do mês de `dataPrevista`, a UI pergunta "Considerar renda do mês atual?" (`PagamentoMesDialog.kt`) antes de decidir qual data usar na `Renda` gerada — "Sim" usa hoje, "Não" usa a `dataPrevista` original. `dataPagamento` sempre grava a data real (hoje), independente da escolha.
- **Atraso "arrasta"**: calculado em tempo de leitura (`ARecebimentoComDados.isAtrasado()`, `!pago && dataPrevista < hoje`), nunca armazenado — não some sozinho, só quando pago ou excluído. Item atrasado aparece com fundo `errorContainer` em `ARecebimentoListItem`.
- **Exclusão em cascata reaproveitada** (`deleteARecebimentoForward`, mesma regra das Features 1/2): apaga a ocorrência e todas as futuras já geradas da cadeia. Adicionalmente, qualquer ocorrência já paga dentro da cadeia excluída também apaga a `Renda` que ela gerou (`rendaGeradaId`) — consequência natural de a cadeia sempre incluir a própria ocorrência inicial, mesmo quando não há recorrência (`PONTUAL`).
- **Ícone de notificação na Home** (sino com `Badge` de contagem, ao lado do chip de filtro): abre um diálogo listando os itens atrasados (`HomeViewModel.arecebimentosOriginais` filtrado); tocar num item fecha o diálogo e navega pra "A Receber" já com aquele item selecionado (`Routes.ARecebimento.createRoute(highlightId)` — nav arg opcional, `ARecebimentoListViewModel` abre o diálogo de edição automaticamente quando o item aparece na lista).

**Categoria por Estabelecimento** ("Feature 1" da terceira leva de planejamento): unifica como toda `Compra` recebe categoria — antes só `FIXA`/`PARCELADA`/`RAPIDA` tinham `categoriaId`; `VARIAVEL` nunca teve (categoria só existia por produto/item).
- **`EstabelecimentoEntity.categoriaId`** (nullable, sem valor padrão — mesma `CategoriaEntity` de Produto/Compra): editável no detalhe do estabelecimento (linha "Categoria: X" clicável abaixo do nome em `EstablishmentSummaryCard`, abre `CategoryPickerDialog`) e no cadastro rápido (`AddEstablishmentDialog`, botão de categoria opcional).
- **Auto-preenchimento da categoria em compra `VARIAVEL`**: ao resolver/reconhecer o estabelecimento — tanto no scan de NFC-e (`CompraRepository.save`, usa a `categoriaId` do estabelecimento já cadastrado, se houver) quanto no cadastro manual (`ManualPurchaseEntryViewModel.onEstabelecimentoNomeChanged`/`onEstabelecimentoSugestaoSelecionada`, só quando `tipoCompra == VARIAVEL`) — a `categoriaId` do estabelecimento é copiada pra `categoriaId` da compra. Continua editável depois, direto no formulário (`ManualPurchaseEntryScreen`, mesmo botão de categoria que `FIXA`/`PARCELADA`/`RAPIDA` já usavam, agora também dentro do bloco `VARIAVEL`). Sem estabelecimento com categoria, a compra fica `categoriaId = null` ("Sem categoria") — **sem fallback artificial**.
- **Backfill retroativo** (`EstabelecimentoRepository.updateCategoria` → `CompraDao.backfillCategoriaForEstabelecimento`): toda vez que a categoria de um Estabelecimento é definida/trocada, todas as compras `VARIAVEL` **já existentes** daquele estabelecimento que ainda estão `categoriaId IS NULL` são atualizadas em lote pra essa categoria — compras que já tinham categoria própria (herdada antes ou editada manualmente) não são sobrescritas (`WHERE categoriaId IS NULL` na query).
- **Conflito de categoria no vínculo CNPJ**: ao vincular um estabelecimento sem CNPJ a um com CNPJ (`EstablishmentDetailViewModel.onLinkTargetSelected`), se os dois têm categorias diferentes e não-nulas, um `AlertDialog` (`categoria_conflict_*` strings) pergunta qual prevalece antes do `ConfirmDialog` de sempre; a escolhida é aplicada ao estabelecimento com CNPJ (que sobrevive ao merge) **depois** do merge (`linkEstabelecimento` primeiro, `updateCategoriaEstabelecimento` depois — assim o backfill do `updateCategoria` já roda sobre as compras recém-migradas pro estabelecimento com CNPJ). Sem conflito (uma das categorias nula, ou iguais), o fluxo pula direto pro confirm de sempre, sem diálogo extra.
- **"Gasto por Categoria" ganhou dois modos** (`CategorySpendingMode.POR_COMPRA`/`POR_PRODUTO`, chips no topo da tela, **Por Compra é o padrão**): "Por Compra" soma `Compra.valorTotal` agrupado por `Compra.categoriaId` (todos os 4 tipos, uniforme); "Por Produto" é o gráfico de sempre, item a item, só `VARIAVEL` (inalterado). `CategorySpendingViewModel` computa as duas agregações em paralelo (baratas) e o state só expõe a ativa via `CategorySpendingState.categorias` (computed property por `modo`).
- **Home "Valor gasto"** passou a usar a mesma lógica "Por Compra" (ver nota em "Contribuição nos totais" acima).

**Divisão de Conta** ("Feature 2" da terceira leva de planejamento, depende de "Categoria por Estabelecimento"): permite lançar uma compra que só é parcialmente "sua" — o resto vira cobrança pros outros participantes via A Receber. Disponível em `Variável`/`Fixa`/`Parcelada`/`Rápida`, **só configurável na criação** — o switch "Dividir conta" some inteiro do formulário em modo edição (`if (!state.isEdicao)` em `ManualPurchaseEntryScreen`), então a divisão de uma compra já salva não pode ser adicionada, removida nem editada depois (trade-off deliberado — ver "Limitações conhecidas" abaixo).
- **Reaproveita `FonteRenda` como "pessoa"**: participantes são selecionados/cadastrados na mesma tabela/autocomplete-ou-cria já usado em Renda e A Receber (`FonteRendaDao.findByNome`), sem entidade "Pessoa" nova.
- **`CompraEntity.dividida: Boolean`** (default `false`) + nova tabela **`DivisaoContaEntity(compraId, fonteRendaId, valor)`** — uma linha por participante (não inclui o dono da conta; a parte dele já está implícita no `valorTotal` da própria `Compra`).
- **`Compra.valorTotal` vira "sua parte"**: `CompraRepository` sempre recebe o **valor total pago** (soma dos itens pra `VARIAVEL`, campo "Valor" pras demais) e, se houver participantes, grava `valorTotal = valorPago - participantes.sumOf { valor }`. Para `VARIAVEL`, os **itens continuam com o preço cheio** (sem escalar) — só o agregado da compra reflete a parte do dono; a agregação "Por Compra" (Feature 1) já lida com isso automaticamente, usando `valorTotal` direto.
- **Divisão igualitária com valores editáveis**: switch "Dividir igualmente" recalcula `valorPago / (participantes.size + 1)` pra cada participante sempre que um é adicionado/removido ou o switch é ligado — nunca ao editar um valor manualmente (edição manual não desliga o switch, só "descola" aquele valor específico do recálculo automático até o próximo add/remove/toggle).
- **Geração do A Receber** (`CompraRepository.criarDivisaoConta`, privado): um `ARecebimentoEntity(tipo = PONTUAL, compraOrigemId = compraId)` por participante, `descricao` gerada automaticamente ("Sua parte em `<estabelecimento ou nome da despesa>`, `<data>`"), `rendaCategoriaId` resolvido/criado a partir do **nome** da categoria da despesa (`RendaCategoriaRepository.addCategoriaERetornarId`, novo método, mesmo padrão do `CategoriaRepository.addCategoriaERetornarId` já usado em Produto) — categoria de despesa nula vira uma `RendaCategoria` chamada "Sem categoria" (decisão pragmática, não coberta explicitamente pelo planejamento). `dataPrevista` = a data daquela compra/parcela específica.
- **`ARecebimentoEntity.compraOrigemId: Long?`** (nullable, mesmo padrão do `rendaGeradaId` já existente) — rastreia de volta a `Compra` que originou aquele A Receber.
- **Propagação em `FIXA`/`PARCELADA`**: `gerarLoteFixa`/`criarSerieParcelada` ganharam parâmetros `dividida`/`participantes` — cada ocorrência do lote inicial de 12 (`FIXA`) ou cada parcela da série completa (`PARCELADA`, **incluindo as retroativas** de `parcelasJaPagas` — geram A Receber com `dataPrevista` no passado, podendo nascer já "atrasado"; comportamento aceito como esperado) gera seu próprio conjunto de A Receber. **Extensão automática** (`verificarEEstenderSeriesFixa`, roda no `init` da Home) também propaga: lê o template de participantes da série a partir das `DivisaoContaEntity` já gravadas na última ocorrência (`divisaoContaDao.getByCompraIdOnce`), já que a extensão automática não passa pelo formulário.
- **Exclusão em cascata**: `deleteCompraForward`/`deleteCompra` (`CompraRepository`) agora também apagam os A Receber ligados via `compraOrigemId` — mas só os **ainda não pagos** (mesma regra de `ARecebimentoRepository.deleteARecebimentoForward`); os já pagos permanecem, com `compraOrigemId` órfão (igual ao padrão já existente de `rendaGeradaId` sobrevivendo à exclusão da série de origem).
- **Exibição**: `PurchaseDetailScreen` mostra uma seção "Divisão da conta" (participante + valor de cada um) quando `compra.dividida` — busca via `GetDivisaoContaUseCase`/`DivisaoContaDao.getByCompraId` (join com `fontes_renda` pro nome).
- **Limitações conhecidas (trade-off deliberado, fora do planejamento original)**: como a UI de divisão não aparece em modo edição, **editar uma compra `FIXA`/`PARCELADA` já dividida (nome/valor/categoria) não sincroniza os A Receber já gerados** — eles continuam com os valores/descrição originais. O planejamento original previa propagação de edição pros A Receber pendentes; não foi implementado por complexidade/tempo. Também: **divisão fica restrita ao fluxo de cadastro manual** (`ManualPurchaseEntryScreen`) — uma compra escaneada por NFC-e não pode ser dividida diretamente (só a categoria dela é auto-preenchida, ver acima); e o **backup/importação JSON ainda não inclui `DivisaoContaEntity` nem `ARecebimentoEntity`** (gap pré-existente — A Receber já não era coberto pelo backup antes desta leva; não expandido aqui).

## Navegação e telas

Bottom bar (5 abas, sempre visível nelas, oculta nas demais telas), **Início centralizado**: **Registros** (carrinho), **Renda** (`Payments`), **Início** (Home, no meio), **Análise** (`BarChart`), **Configurações**.

- **Análise** (`AnaliseScreen`/`AnaliseViewModel`, nova aba, rota `analise`): herdou da Home os cards **Produtos** (top 5 por gasto no período) e **Estabelecimentos** (top 5 por gasto no período, item clicável abre o detalhe direto), cada um com seta pra lista completa — mesmo filtro de período local (semeado da Home, ver "Filtro de data" acima). Ganhou também um card de entrada pra **"Comparação de Gastos"** no topo (antes só acessível pelo card "Valor gasto" da Home, que foi removido).
- **Renda**: lista de entradas do período filtrado (calendário), FAB "+" abre `AddEditRendaDialog` (descrição, valor, categoria via picker, fonte com autocomplete-ou-cria, data e switch "Recorrente" — os dois últimos só aparecem na criação, tipo/recorrência não são editáveis depois).
- **Configurações** virou uma tela **em seções sanfona (accordion)**, cada uma colapsada por padrão (`SettingsSection`, estado `expanded` local por seção): **Despesas** (Produtos, Categorias de Produtos, Estabelecimentos, Compras Parceladas), **Renda** (Fontes, Categorias de Renda, A Receber), **Dados** (Exportar dados). **Fontes** é o ranking por valor recebido (mesmo padrão zero-default dos Estabelecimentos, FAB "+" pra cadastrar direto; clique abre **Detalhe da Fonte** com os lançamentos daquela fonte no período) e **Categorias de Renda** é o CRUD igual ao de Categorias de produto, reaproveitando o mesmo `CategoryListItem` generalizado.

- **Home**: FAB de câmera abre um menu (`DropdownMenu`) com "Escanear NFC-e" e "Adicionar manualmente" + chip de filtro e sino de alertas de A Receber no topo + `StatCard` "Saldo" (ver "Saldo e Balanço" abaixo — é o único card que sobrou na Home; "Valor gasto" e os cards de Produtos/Estabelecimentos foram todos removidos/movidos pra Análise).
- **Registros**: lista de compras, filtro de mês (flutuante), clique abre detalhe da compra (resumo + itens + excluir); FAB próprio ("+") pra "Adicionar manualmente".
- **Configurações**: ver reorganização em seções logo acima. **A Receber**: lista todos os `ARecebimento` (sem filtro de período — itens atrasados nunca somem sozinhos), FAB "+" abre formulário parecido com o de Renda mas com seletor de tipo (Pontual/Fixa/Parcelada, só na criação) e botão "Marcar como pago" no modo edição.
- **Scanner**: lê QR Code, busca HTML da NFC-e, salva, mostra diálogo de sucesso, navega pro detalhe da compra salva (com `popUpTo` removendo o Scanner da pilha). Enquanto a nota é buscada/processada, um overlay escuro com `CircularProgressIndicator` cobre a câmera (`ScannerState.isLoading`). **`NfceHtmlParser` nunca lança exceção quando a página não tem o formato esperado** — cada campo cai num default (`""`/`0.0`/lista vazia) — então uma nota inválida (ex. QR Code rejeitado pela própria Sefaz por assinatura/digest incorreto: a página retornada nesse caso é só o formulário de busca "Consulta Pública por QR Code", sem nenhum dos seletores que o parser procura) resultava numa **compra vazia salva silenciosamente**, sem erro nenhum. Corrigido em `ScannerViewModel.onQrCodeRead`: depois do parse, se `chaveAcesso`, `estabelecimento.nome` e `produtos` vierem todos vazios, trata como nota inválida (`scanner_error_invalid_nota`) e **não salva** — mesmo caminho de erro (Toast) já usado pros outros casos (HTML nulo, exceção de rede/parse).
- **Cadastro/edição manual de compra** (`ManualPurchaseEntryScreen`, rota `manual_purchase_entry?compraId={compraId}`, `compraId = 0` = criar): chips de tipo (Variável/Fixa/Parcelada, ocultos em modo edição — tipo é imutável após salvar) escolhem qual formulário aparece. **Variável**: campo de estabelecimento com autocomplete (+ apelido, só exibido quando o nome digitado não bate com um estabelecimento já existente), date picker livre (Material3 `DatePickerDialog`), lista de itens (autocomplete de produto + confirmação de novo produto + bloqueio de item duplicado na mesma compra + cálculo bidirecional quantidade/valor unitário/valor total), "Salvar" grava tudo de uma vez. **Fixa/Parcelada**: nome, valor, categoria (picker de produto) e, só na Parcelada, total de parcelas + parcelas já pagas (esse último oculto em edição). Reaberta em modo edição pelo botão "Editar" no topo do detalhe da compra, visível só quando `compra.origem == MANUAL`.
- **Detalhe de compra**: quando `origem == MANUAL`, mostra selo "Cadastro manual" e o botão "Editar" no topo (CNPJ/endereço já ficam ocultos "de graça" porque estabelecimentos manuais gravam `cnpj = ""`/`endereco = ""`, reaproveitando o `isNotBlank()` que já existia no `PurchaseSummaryCard`). Quando `tipo != VARIAVEL`, troca a lista de itens por um card com nome/categoria/valor e, se `PARCELADA`, a lista de todas as parcelas da série (`ParcelaRow`, destaca a parcela atual); excluir uma Fixa/Parcelada usa a mensagem de confirmação de cascata (avisa que apaga essa e as futuras já geradas) em vez da mensagem simples.
- **Detalhe de produto**: resumo (qtd, preço médio, maior/menor preço pago), categoria (botão "+" pra atribuir, 1 categoria por produto), histórico de compras daquele produto.
- **Detalhe de estabelecimento**: resumo (CNPJ, endereço, total gasto, **apelido editável** via lápis), gráfico de gasto mês a mês, lista de compras naquele estabelecimento (filtro de mês). Quando `cnpj` está vazio, mostra botão "Vincular a um estabelecimento com CNPJ" → `LinkEstablishmentDialog` (picker) → `ConfirmDialog` (irreversível) → funde no estabelecimento escolhido e volta pra tela anterior.
- **AnalyticsScreen**: componente de tela genérico (título + `List<ChartEntry>` + loading) reaproveitado 3x — comparação mensal geral, gasto por estabelecimento (mensal) e gasto por categoria. `AnalyticsContent`/`analyticsChartItems` são extraídos para poder compor dentro de outras `LazyColumn` (ex. detalhe de estabelecimento mistura resumo + gráfico + lista de compras numa única lista rolável).

## Exportação de dados (backup JSON) — Feature 8

Botão "Exportar dados (JSON)" em Configurações (`SettingsScreen`/`SettingsViewModel`). `BackupRepository.exportBackup()` pega um snapshot único (`Flow.first()`, não uma exportação "ao vivo") de `EstabelecimentoRepository.getAll()`, `ProdutoRepository.getAllProdutos()`, `CategoriaRepository.getCategorias()` e `CompraRepository.getCompras()` (de onde extrai `CompraEntity` e `ItemCompraEntity` — sem query nova, já vem embutido em `CompraCompleta`), serializa num único `ShopControlBackup` (kotlinx.serialization) e grava em `context.cacheDir/backups/shopcontrol_backup_<data>.json`. Devolve um `content://` `Uri` via `FileProvider` (`res/xml/file_paths.xml` + `<provider>` no manifest, authority `${applicationId}.fileprovider`) — a tela então dispara `Intent.ACTION_SEND` (menu nativo de compartilhamento), a mesma sequência "salva local, depois compartilha" pedida no planejamento.

**As 5 entidades Room (`EstabelecimentoEntity`, `ProdutoEntity`, `CategoriaEntity`, `CompraEntity`, `ItemCompraEntity`) e o enum `OrigemCompra` ganharam `@Serializable` diretamente** (kotlinx.serialization), em vez de uma hierarquia paralela de DTOs — evita duplicar os campos e o backup sempre reflete o schema atual automaticamente (era exatamente o requisito: "todos os campos vigentes no schema no momento da implementação").

**Os dois itens em aberto do planejamento (8.3) foram resolvidos com a opção mais barata, sem exigir decisão do usuário**: o JSON já é estruturado pensando numa futura importação (listas por entidade, relacionamentos preservados por id) porque essa é a estrutura natural de qualquer forma; e o arquivo inclui `schemaVersion` (constante `BACKUP_SCHEMA_VERSION` em `ShopControlBackup.kt`, hoje = 6, acompanha a versão do `AppDatabase`) e `exportedAt`.

**Importação de dados (JSON)** — botão próprio em Configurações → Dados, ao lado do de exportar: abre o seletor de arquivos do Android (`ActivityResultContracts.OpenDocument`, filtro `application/json`), mostra um `ConfirmDialog` de aviso, e chama `BackupRepository.importBackup(uri)`. `ShopControlBackup` ganhou 3 listas novas (`rendaCategorias`, `fontesRenda`, `rendas`, todas com `= emptyList()` default — backups antigos sem essas chaves continuam decodificando normalmente) e `RendaEntity`/`RendaCategoriaEntity`/`FonteRendaEntity` ganharam `@Serializable`, então a exportação agora também inclui Renda (antes só cobria as 5 entidades originais).
- **Toda a importação roda dentro de `AppDatabase.withTransaction { }`** (tudo ou nada) e trata todo `id` do JSON como um **id local só daquele arquivo**, nunca como o id real do banco — necessário porque o import roda contra um banco já em uso, com seus próprios autoincrements. Para cada entidade, dedup-ou-cria (mesmo padrão já usado em todo o app: `findByCnpj`/`findByNome` antes de inserir) e guarda um `Map<idAntigo, idNovo>`; entidades que referenciam outra (produto→categoria, compra→estabelecimento/categoria, item→compra/produto, renda→categoria/fonte) são remapeadas usando esses mapas na hora de inserir.
- **Cadeias de recorrência (`origemRecorrenteId`) são preservadas**: como `backup.compras`/`backup.rendas` são processados **na ordem em que aparecem no array**, o mapa de ids já contém a entrada do "pai" no momento em que um "filho" da mesma cadeia é processado — um JSON de importação com uma série `FIXA`/`PARCELADA`/Renda recorrente precisa listar as ocorrências em ordem (raiz primeiro), senão a referência não resolve e a linha é pulada (best-effort: entidades com referência não resolvida são silenciosamente ignoradas, não abortam a transação inteira).
- **`ProdutoEntity.categoriaId = 0` (sentinela "sem categoria") nunca é remapeado** — só valores reais de categoria passam pelo mapa, preservando a mesma convenção documentada acima.

**Planilha pessoal → JSON de importação**: a pedido do usuário, a planilha `Finanças 2026` (mesma que inspirou a Feature 1 do novo planejamento) foi convertida para o formato de importação via um script PowerShell ad-hoc (Excel COM Automation, já que o ambiente não tinha Python) — não faz parte do código do app, é uma conversão pontual. Decisões de mapeamento tomadas (documentadas ao usuário, não óbvias a partir do schema): estabelecimento único sintético "Importado (Finanças 2026)" pra todas as compras (a planilha não distingue lojas); categorias "Role: X" (dezenas de variações de nome de evento) colapsadas numa única categoria "Rolê"; linhas "Contas variáveis" da planilha (sem itens/produto formal) viram uma `Compra VARIAVEL` com um item só (produto = a descrição da linha); "Contas fixas" usam o valor da primeira ocorrência observada (a planilha deixa o valor derivar mês a mês, o app assume valor fixo); "Contas parceladas" cujo início (`Parc. Atual` na primeira aparição) cai antes de janeiro/2026 têm a âncora calculada retroativamente por aritmética de data (pode cair em 2025), não truncada — outra abordagem geraria parcelas fantasmas. Arquivo gerado: `import_financas_2026.json` na raiz do projeto (não versionado, é dado pessoal).

## Fluxo de build (sempre seguir isso)

- **Sempre compilar e instalar no dispositivo conectado após qualquer alteração de código**, sem esperar o usuário pedir: `adb devices -l` pra confirmar conexão, depois `./gradlew.bat :app:installDebug --console=plain`.
- O daemon do Gradle às vezes é derrubado externamente no meio do build ("Daemon is stopping immediately stop command received") — se isso acontecer, repetir o comando com `--no-daemon` costuma resolver.
- Rodar em background (`run_in_background`) para builds grandes, já que costumam levar 1-2 min.
- Se o dispositivo não estiver conectado (`adb devices -l` vazio), compilar mesmo assim (`compileDebugKotlin`) pra validar o código, e avisar que falta instalar.
- **O daemon do ADB wireless também é derrubado externamente com frequência** (`adb devices -l` retorna vazio sem nenhum comando ter mudado nada). Nesse caso, **não tentar reconectar** (`adb kill-server`, `adb start-server`, `adb mdns services` etc.) — decisão explícita do usuário, que rejeitou essas tentativas duas vezes na mesma sessão. Repetir `adb devices -l` puro no máximo uma ou duas vezes e, se continuar vazio, seguir em frente só com a compilação e avisar que a instalação ficou pendente.
